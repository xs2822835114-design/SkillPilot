# SkillMap 项目代码学习指南（面向初学者）

> 目标读者：刚接触本项目、想弄懂「这段代码在干嘛、为什么这么分层」的初学者。
> 建议先读：`项目规划/SkillMap_阶段1_基础工程与Agent最小闭环_详细计划.md`（业务目标）与 `docs/api_v1.md`（接口契约）。
> 本文只讲**当前已落地的代码**（阶段 1：基础工程 + Agent 最小闭环），并尽量用大白话。

---

## 1. 这个项目是什么

SkillMap 是一个「**个人技术栈成长智能体**」：用户告诉它自己的技术目标和背景，它帮你做能力画像、缺口分析、学习规划等。整体规划分 6+ 个阶段，**目前只完成了阶段 1**，即：

> 跑通「用户在浏览器里发一句话 → 后端 Flask 收到 → LangGraph 编排 → 单个 Agent 处理 → 返回标准 JSON」的最小闭环，并支持**会话上下文恢复**（重启后端也不丢）。

所以你现在看到的**绝大部分逻辑还是"占位/最小实现"**，后面阶段的业务 Agent（画像、缺口、规划等）还没有真正实现。理解这一点，你就不会困惑"怎么回复这么简陋"。

**技术栈一览**

| 层 | 用到的技术 |
| --- | --- |
| 前端 | Vue 3 + Vite + Pinia + Vue Router + axios |
| 后端 | Python + Flask + LangGraph + Pydantic v2 + psycopg |
| 持久化 | PostgreSQL（LangGraph PostgresSaver 存会话）、浏览器 localStorage（前端本地目录） |

## 2. 目录结构指南

### 2.1 顶层

```
SkillPilot/
├── app/              # 后端主应用（Python 包）
├── frontend/         # 前端（Vue3 单页应用）
├── scripts/          # 运维脚本（如 init_db.py 建表）
├── tests/            # 后端测试
├── docs/             # 文档
└── 项目规划/          # 计划书、阶段计划、接口文档
```

### 2.2 后端 `app/` —— 按"层"分目录（这是最重要的设计）

```
app/
├── __init__.py        # create_app：Flask 应用工厂，把所有东西组装起来
├── __main__.py        # `python -m app` 的启动入口
├── config.py          # 配置：读取 .env，生成 Config 对象
├── contracts.py       # 跨层共享的契约常量（如合法意图枚举）
│
├── api/               # 【接入层】只做 HTTP 入/出，不做业务
│   ├── schemas.py     #   请求体校验（Pydantic）
│   ├── errors.py      #   统一错误码 + 统一错误响应
│   └── routes/
│       ├── health.py  #   GET /health
│       └── chat.py    #   POST /api/v1/chat
│
├── orchestrator/      # 【编排层】LangGraph 图与运行时状态
│   ├── state.py       #   SkillMapState：一次会话的"总状态"
│   └── graph.py       #   把节点连成图并编译
│
├── agents/            # 【Agent 层】真正干活的智能体
│   ├── base.py        #   Agent 基类（定义契约）
│   └── orchestrator_agent.py  # 阶段 1 唯一 Agent：识别意图+回复
│
├── persistence/       # 【持久化层】
│   ├── db.py          #   数据库连接
│   ├── checkpointer.py#   LangGraph 会话保存器（Postgres / 内存）
│   └── thread_store.py#   threads 表读写
│
└── middleware/        # 【横切层】
    ├── trace.py          # trace_id 生成/传递
    └── logging_middleware.py
```

**核心设计：分层 + 单向依赖。** 上层只能调下层，下层不能反向 import 上层：

```
api(接入) → orchestrator(编排) → agents(智能体) → persistence(持久化)
```

这样后续加新 Agent 时，**接入层和管道不用改**，只要往编排图里塞新节点。

### 2.3 前端 `frontend/src/` —— 同样分层


## 3. 一条消息的完整旅程（最重要的一节）

> 你把「我想转向 AI 应用开发」敲进去并按回车，到看见回复，发生了什么？

### 3.1 前端部分

1. **[ChatComposer.vue]** 的输入框拿到文字，按回车触发 `emit('send', text)`。
2. **[ChatView.vue]** 收到后调用 `chat.sendMessage(text)`（Pinia store 的 action）。
3. **[stores/chat.js] `sendMessage`**
   - 先在本地把**用户消息**推进 `thread.messages`，界面立刻显示（体验好）。
   - 调 `sendUserMessage(...)`，这是 **service 层**。
4. **[services/chatService.js] `sendUserMessage`**
   - 调 `toChatPayload(...)` 组装**符合后端契约**的请求体（字段转 snake_case）。
   - 调 **API 层** `sendChatMessage(payload)` 真正发请求。
   - 拿到原始响应后用 `normalizeReply()` 转成**前端视图模型**（`raw.workflow_status` → `workflowStatus`），页面只认这个。
5. **[api/chat.js] + [api/http.js]**
   - `http.js` 是 axios 实例，响应拦截器负责**解包统一信封** `{code, message, data, ...}`：
     - `code === 0` → 直接返回 `data`：
     - `code !== 0` → 抛 `ApiError`（带 code/message/trace_id）。
   - 所以上层永远拿不到信封，只拿数据或异常。

### 3.2 后端部分

6. Flask 路由 **[api/routes/chat.py] `POST /api/v1/chat`**：
   - 取 JSON → 无效抛 `40001`。
   - 用 Pydantic **[api/schemas.py] `UserRequest`** 校验字段（缺 message / 超长 / 非法 ID 都抛 `42200`）。
   - 调 `thread_store.upsert_thread(...)` 记录会话元信息（尽力而为，失败不阻断）。
   - 调 `_get_graph()`：**惰性**构建并缓存 LangGraph 图（含 checkpointer）。
   - `graph.invoke({...}, config={"configurable": {"thread_id": ...}})` 执行编排。
   - 把最终 **State** 用 `_build_result()` 映射成响应契约（`route/steps/reason/reply/...`）。
7. 图 `graph.py` 的结构是：

   ```
   START → orchestrator_agent → END
   ```

8. **[agents/orchestrator_agent.py] `invoke(state)`** 是这个阶段唯一的"大脑"：
   - 从 State 里拿 `message`、`intent_hint`、`messages`（历史）。
   - **优先走 LLM**（`_run_with_llm`）：调 DeepSeek，用 `with_structured_output` 强制输出 `AgentOutput` 结构化 JSON。
   - **LLM 不可用或报错 → 回退到规则**（`_fallback`）：用关键词表粗略判断意图，拼一段"阶段 1 占位"的回复。
   - 把用户消息 + 助手消息追加进 `messages`，并写回 State。
9. **[persistence/checkpointer.py] `get_checkpointer`**
   - 配置 `postgres` → 用 `PostgresSaver` 连接 PostgreSQL，并在**初始化时** `checkpointer.setup()` 建表。
   - 配置 `memory`/没配 DB → 用 `InMemorySaver`（进程内，重启即丢）。
   - LangGraph 会根据 `thread_id` 自动把 **State 快照**存到 checkpointer，下次同 `thread_id` 时自动恢复历史 → 这就是**上下文恢复**的原理。

### 3.3 兜底设计（阶段 1 的精髓）

> **无论 LLM/DB 出什么问题，接口都必须返回标准 JSON，绝不裸抛异常给前端。**

- Agent：LLM 失败 → 规则兜底，`code` 仍为 `0`（正常回答了）。
- 后端：未捕获异常 → `errors.py` 统一兜底 `50000`（记录堆栈，但对外只说"服务器内部错误"，不泄露细节）。
- 前端：`ApiError` → store 在消息列表里插入一条 error 气泡，页面不白屏。

## 4. 四个必须理解的概念

### 4.1 State（LangGraph 的“总账本”）

`SkillMapState`（[orchestrator/state.py]）是一个 `TypedDict`，描述**一次会话运行时的全部状态**：

```python
class SkillMapState(TypedDict, total=False):
    messages          # 对话历史（本轮 + 之前，最重要）
    user_id, thread_id
    message, intent_hint, intent
    skill_profile / skill_gap / learning_plan / ...  # 阶段1占位，后续阶段填充
    retrieved_evidence / memory_context
    current_agent, workflow_status, error
```

要点：字段**一次性定义完整**了（为后续阶段预留），但阶段 1 只用到其中一小部分。图里**每个节点都能往 State 里塞字段**，下一个节点读得到。

### 4.2 节点与图（graph.py）

- 节点 = 一个函数（这里就是 `orchestrator.invoke`）。
- 边 = 执行顺序：`STATE -> orchestrator_agent -> END`。
- `builder.compile(checkpointer=...)`：checkpointer 绑定后，LangGraph 自动负责"保存/恢复 State"。

> 后续加业务 Agent，就是在 `builder.add_node("gap_agent", ...)` 再连几条边，管道本身不用动——这就是为什么阶段 1 要先铺管道。

### 4.3 Checkpointer（会话持久化）

- **作用**：按 `thread_id` 存档每个步骤后的 State。
- **PostgresSaver**：重启后端不掉线（已落地）；`InMemorySaver`：仅开发/测试。
- **为什么放在"启动期"建表**：`get_checkpointer()` 只在 `_get_graph()`（首次请求）或启动时执行 `setup()`，避免每次写入都重复建表。

### 4.4 统一契约（前端与后端的地基）

后端所有接口返回统一信封；前端 `http.js` 统一解包、`errors.py` 统一错误。**契约在阶段 1 就冻结**，前后端各层都围绕它开发，避免后期返工。

前端这边，`utils/threadStorage.js` 用 `localStorage` 维护线程目录，是因为**阶段 1 后端还没有"线程列表"接口**。文件注释明确写了：以后后端出了接口，只替换这一个模块即可，上层不动。

## 5. 如何运行（动手跑起来）

### 后端

```bash
# 1. 配置环境变量
cp .env.example .env
#   注意：LLM_API_KEY 不是必须的（没配也能跑，走规则兜底）

# 2.（可选）初始化数据库（配置了 DATABASE_URL 时执行一次）
.venv/bin/python -m scripts.init_db

# 3. 启动（默认 5000；macOS 常用 8081 避开 AirPlay）
PORT=8081 .venv/bin/python -m app
```

### 前端

```bash
cd frontend
npm install
# 让前端开发服务器把 /api 代理到后端（端口要一致）
echo "VITE_DEV_PROXY_TARGET=http://localhost:8081" >> .env
npm run dev   # 打开 http://localhost:5173/
```

验证：后端 `GET /health` 应返回 `{"code":0,"data":{...}}`；在页面发一句话应得到回复。

> 注意：Flask 只返回 `code` 信封，前端跨域靠 Vite 的 dev 代理解决（见 `frontend/vite.config.js`）。

## 6. 调试与排查技巧

| 现象 | 可能原因 | 查哪里 |
| --- | --- | --- |
| 页面提示"无法连接后端" | 后端没启动 / 端口不一致 | 看后端终端日志；`curl http://localhost:8081/health` |
| 发消息返回 500 | 后端 500，多半是数据库没就绪 / 建图异常 | 看后端日志堆栈；确认 PostgreSQL 是否在运行 |
| 回复很"简陋" | 走了规则兜底（LLM 没配 key 或 key 失效） | 看 `app.agents.orchestrator_agent` 的 warning 日志 |
| 上下文没恢复 | 用了 `memory` 后端，或前后端 thread_id 不一致 | 确认 `.env` 的 `CHECKPOINTER_BACKEND` |
| 字面字段对不上 | 前后端契约名不同（camelCase vs snake_case） | 该转换在 `services`/`api` 层完成，检查这两层 |

**看请求顺序**：前端 DevTools 的 Network 看请求体/响应体；后端日志按 `END`/`warning` 定位是走了 LLM 还是规则。

## 7. 常见概念扫盲（术语表）

- **LangGraph**：Python 里的"图编排"库，像搭积木一样把节点连成流程，自带状态管理与持久化。
- **Agent（智能体）**：一个"会做判断 + 产出结果的函数/对象"。阶段 1 只有一个 `OrchestratorAgent`。
- **State**：一整套跨节点的数据载体（见 4.1）。
- **Checkpoint / Checkpointer**：把 State 定时"存盘"，用来恢复会话（见 4.3）。
- **Structured Output**：让 LLM 只输出符合某个 schema（Pydantic 模型）的 JSON，方便程序直接使用，不用解析自由文本。
- **Pydantic**：Python 数据校验库，后端用它校验请求（`UserRequest`）和 Agent 输出（`AgentOutput`）。
- **Pinia**：Vue 的全局状态库，类似一个"全局变量池"，页面组件都能读写。
- **统一信封**：`{code, message, data, trace_id}` 这层外壳，前后端都围绕它做解包/包装。
- **snake_case / camelCase**：`workflow_status`（后端）↔ `workflowStatus`（前端），负责在 service/api 层互相转换。

## 8. 建议的学习路线

1. **先跑起来**（第 5 节），用 UI 发两条消息，感受上下文恢复。
2. 用 POSTMAN/curl 打 `POST /api/v1/chat`，观察统一信封。
3. 顺着第 3 节的调用链，从前端 `sendMessage` → `sendUserMessage` → 后端 `chat` → `graph` → `agent` → 写回，**一步一步跟一遍**。
4. 给后端关掉 LLM（注释 `.env` 的 key），看规则兜底如何工作。
5. 读 `docs/api_v1.md`，把契约和代码逐一对应。
6. 最后再去读规划文档，看后续阶段会把哪些"占位"替换成真实现。
